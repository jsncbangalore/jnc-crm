# Production Secrets, Key Management & Rotation Runbook

## 1. Secrets Management Policy

In production environments (e.g., Render, AWS, Hostinger, or Kubernetes), security keys **must never be automatically generated or regenerated by deployment blueprints (`sync: false`)**. 

All production secrets must be generated once by a designated security administrator, entered manually into the hosting provider's environment settings, and securely stored in an encrypted organizational password manager (e.g., 1Password, Bitwarden, AWS Secrets Manager).

### Critical Application Secrets Overview

| Secret Key | Format / Length | Purpose | Where Managed |
| :--- | :--- | :--- | :--- |
| `JWT_SECRET` | 64-char hex / 256-bit | Signs short-lived access JWT tokens | Hosting dashboard env vars |
| `JWT_REFRESH_SECRET` | 64-char hex / 256-bit | Signs long-lived `crm_refresh_token` cookies | Hosting dashboard env vars |
| `ENCRYPTION_KEY` | 32-byte hex (64 chars) | AES-256-GCM encrypts sensitive DB fields (SMTP passwords) | Hosting dashboard env vars |
| `OTP_SECRET` | Min 32 chars | Signs transient 2FA challenges & phone OTPs | Hosting dashboard env vars |
| `BACKUP_ENCRYPTION_KEY` | Min 32 chars | Encrypts automated database backups at rest | Hosting dashboard env vars |
| `DATABASE_URL` | PostgreSQL URI | Primary database connection string | Hosting dashboard env vars |

## 2. Secret Rotation Procedures & Impact Analysis

### A. Rotating `JWT_SECRET`
- **Impact**: Low / Non-Disruptive. Immediately invalidates all active access tokens. 
- **User Experience**: Because clients store a valid refresh cookie, the frontend automatically intercepts the next API call, hits `/api/v1/auth/refresh`, receives a new access token signed with the new secret, and proceeds without requiring the user to re-type credentials.
- **Procedure**:
  1. Generate new 64-character hex secret: `openssl rand -hex 32`.
  2. Update `JWT_SECRET` in the hosting environment variables.
  3. Trigger zero-downtime deployment.

### B. Rotating `JWT_REFRESH_SECRET`
- **Impact**: Medium / Session Termination. Immediately invalidates all active user sessions across all companies and platform admins.
- **User Experience**: All users will be logged out on their next navigation or background refresh and must enter their email/password (+ 2FA) again.
- **Procedure**:
  1. Notify users of scheduled session reset if outside maintenance hours.
  2. Generate new secret: `openssl rand -hex 32`.
  3. Update `JWT_REFRESH_SECRET` in hosting dashboard.
  4. Redeploy application.

### C. Rotating `OTP_SECRET`
- **Impact**: Low. Invalidates pending in-flight 2FA verification attempts.
- **User Experience**: If a user is midway through typing a 6-digit SMS/email code at the exact moment of rotation, verification will fail with an expired/invalid message. The user simply clicks "Resend Code" to receive a fresh valid OTP.
- **Procedure**:
  1. Generate secret: `openssl rand -hex 32`.
  2. Update `OTP_SECRET` and redeploy.

### D. Rotating `ENCRYPTION_KEY` (CRITICAL DOWNTIME PROCEDURE)
- **Impact**: **CRITICAL**. `ENCRYPTION_KEY` encrypts database columns at rest (e.g., `MailAccount.password`, tenant SMTP credentials, integration keys). 
- **Danger**: Changing `ENCRYPTION_KEY` in environment variables without re-encrypting existing database records will cause **permanent decryption failure** (GCM authentication tag mismatch), breaking all outbound email notifications and integrations.
- **Procedure**:
  1. Schedule a maintenance window and take a full database snapshot.
  2. Set `OLD_ENCRYPTION_KEY=<current>` and `NEW_ENCRYPTION_KEY=<new_64_hex_secret>`.
  3. Run the database re-encryption migration script (`scripts/ops/reencrypt-database-fields.js`).
  4. Verify all records decrypt cleanly under the new key.
  5. Update `ENCRYPTION_KEY=<new>` in production environment variables and remove `OLD_ENCRYPTION_KEY`.
  6. Restart API and verify email sending and settings page.

### E. Rotating `BACKUP_ENCRYPTION_KEY`
- **Impact**: Low for running service.
- **Procedure**: Update `BACKUP_ENCRYPTION_KEY`. Future database dumps will be encrypted with the new key. Archive the previous key in the password manager with its effective date range so historical backups can be restored if needed.

## 3. Hosting Architecture: Always-On Plan & Persistent Disk Facts

### Always-On Compute Instance vs. Free Ephemeral Tier
1. **Zero Cold-Start Latency**:
   - *Free Tier*: Containers spin down to 0 replicas after 15 minutes of inactivity. When a user navigates to the login page, the incoming request triggers a container cold boot taking 50–90 seconds. This can lead to 504 Gateway Timeouts or failed auth requests.
   - *Always-On Instance*: Keeps at least 1 container running 24/7. Response times remain under 100ms for health checks and API calls.
2. **Database Connection Pool Stability**:
   - Free-tier container cycling frequently closes and re-opens TCP connections, exhausting PostgreSQL pooler slots (Supabase / RDS). Always-on maintains warm, stable connection pools.
3. **Memory & CPU Predictability**:
   - Free instances are subject to aggressive memory throttling. Invoicing PDF generation (`pdfkit`) and streaming require sufficient memory buffers. Always-on instances provide dedicated RAM (e.g. 512MB–2GB) preventing OOM process termination.

### Persistent Disk vs. Cloud Object Storage
1. **Container Ephemerality**:
   - Modern containerized platforms (Render, Heroku, Fly.io, AWS Fargate) use ephemeral file systems. Any files written to the local disk during runtime (such as files saved to `uploads/` or `purchase-documents/`) are **completely wiped upon redeploy, auto-restart, or crash recovery**.
2. **Persistent Disk Volumes**:
   - Attaching a dedicated persistent disk (e.g. `/var/data`) allows local file storage to persist across container redeploys and restarts.
   - *Limitation*: Persistent disks are pinned to a single container instance/zone and cannot be shared across horizontally scaled API replicas.
3. **Private Cloud Object Storage (Recommended Architecture)**:
   - For enterprise scalability, file uploads (purchase bills, invoices, branding assets) are handled via private S3-compatible object storage (AWS S3, Cloudflare R2, or Supabase Storage).
   - Files are stored behind an abstraction layer (`IStorageService`) using tenant-isolated paths (`${tenantId}/${fileUUID}.${ext}`).
   - The application streams the file through authenticated API endpoints with strict headers (`X-Content-Type-Options: nosniff`, `Content-Security-Policy: default-src 'none'; sandbox`) or generates short-lived signed URLs.
